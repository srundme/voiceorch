**Task: Reduce false-positive name latching in callerMemory.ts**

**File:** `artifacts/api-server/src/orchestration/callerMemory.ts` (`NAME_PATTERNS`, `isPlausibleName()`, `latchCallerName()`, ~lines 1283–1384)

**Do not modify:** `caller_facts` schema, supersession logic, `loadCallerContext`, `updateCallerProfile` phases, episode/sentence storage, other latches (language, location, occupation), Tamil/Hindi self-introduction patterns, or the existing stricter "this is X" requirement (must be followed by speaking/calling/here).

### Background
`isPlausibleName()` already rejects most false positives (digits, >3 words, common stopwords, product vocabulary). The one confirmed gap: "I am so confused" currently latches as the name "so confused" because "so" and "confused" aren't yet on the reject list. Additionally, latched names always override LLM-extracted names at call-end — this needs to become conditional, not unconditional.

### Scope

**1. Expand the existing stopword/blocklist in `isPlausibleName()`**
Add: `so`, `confused`, `very`, `still`, `also`, `really`, `just` (extend further as QA finds more). This is an addition to the existing list — do not remove or restructure current checks.

**2. Add a next-token check**
As an additional guard alongside the existing checks in `isPlausibleName()` — not a replacement.

**3. Tier the trust of each match at the point of latch (in-memory, no schema change):**
- Tamil/Hindi patterns, "my name is X", "this is X [speaking/calling/here]" → **Tier A** (high trust)
- "I am X" / "I'm X" → **Tier B** (low trust), only latched after passing the (now-expanded) `isPlausibleName()` checks

**4. Fix the call-end override rule**
- Tier A latch → still overrides LLM extraction (unchanged from today)
- Tier B latch → yields to LLM extraction if the two disagree; used only as a fallback if LLM extraction produces no name at all

**5. Persist the Tier B flag using the existing drop-call cache (no new storage)**
- When a Tier B name is latched, save it as `{ callId, name, tier: 'B' }` in the same short-lived cache/store already used for dropped-call resume (keyed by call ID).
- At call-end — whether the call finished normally or resumed after a drop — check this cache: if an LLM-extracted name exists, it wins over the Tier B name; if none exists (e.g. the call dropped and was never resumed), the Tier B name is used as fallback.
- This entry expires on the same schedule as existing resume data. No changes to `caller_facts` or `caller_profiles` schemas.
