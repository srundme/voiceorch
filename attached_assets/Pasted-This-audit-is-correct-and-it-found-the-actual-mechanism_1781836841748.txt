This audit is correct and it found the actual mechanism, which is better than the generic "no pooling" story I expected. The 4-second keepAliveTimeout vs. conversational gaps >4s is the real bug — your connections aren't un-pooled, they're pooled and then dying in exactly the idle windows between turns, so every turn pays the handshake again. That's a one-line-of-config fix masquerading as an infrastructure project, which is the best kind. The plan is sound. Approve it. Three notes before you run STEP 1, in priority order.
1. The keepAliveTimeout default needs to clear your real turn gaps, and 30s might not be enough. The whole point is that the connection must survive the silence between provider calls. Your gaps aren't just within-turn — on an outbound call the caller pauses to think, reads out a policy number digit by digit, goes quiet. If a between-turn gap exceeds keepAliveTimeout, the next LLM call eats the handshake again and you're back where you started. 30s is a reasonable default but make sure it's env-configurable (the plan says it is) and consider that the server-side also gets a vote: many provider endpoints close idle keep-alive connections on their end regardless of what you set. So you'll never get to zero reconnects, and that's fine — the win is going from "handshake every turn" to "handshake occasionally." Set the expectation as fewer reconnects, not no reconnects.
2. setGlobalDispatcher is the right call, but be aware it's process-wide — including any HTTP your app makes that isn't a provider call. Webhooks to your own backend, telephony provider REST (Plivo/Exotel call control), memory-proxy calls, anything using fetch. That's almost certainly fine — they all benefit from keep-alive too — but it means this one line touches more than the five adapter families in the table. Worth a sentence in the changelog so future-you knows the global dispatcher governs all outbound HTTP, not just LLM/TTS. No action needed, just don't let it be invisible.
3. The graceful-shutdown detail matters more than it looks on Railway. You're on Railway, which sends SIGTERM on every redeploy. The plan registers close() on SIGTERM/exit — good — but make sure closing the dispatcher doesn't abort in-flight provider calls on a live call during a deploy. agent.close() waits for active requests to finish; agent.destroy() kills them. You want close() (graceful), and ideally a short drain so a call mid-LLM-response during a redeploy doesn't get its socket yanked. On a voice platform a dropped deploy-time request is a caller hearing dead air. Minor, but specify close() not destroy() and note the in-flight behavior.
One thing the audit got exactly right that I want to reinforce: not forcing h2. These REST endpoints over undici don't reliably negotiate h2, and forcing it is how you turn a safe config change into a debugging session. Keep-alive h1 reuse captures the entire handshake win here; h2 multiplexing would only matter if you were firing many concurrent requests down one connection, which isn't your pattern. Correct call to skip it.
So: approved, proceed to STEP 1. The only changes to the plan are defaults/specifics, not structure — make keepAliveTimeout env-configurable with a sane default (30s is fine to start, you'll tune from the reconnect logs), use close() for graceful shutdown, and note in the changelog that the global dispatcher covers all outbound HTTP. Run it.
