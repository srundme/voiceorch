Bug: Overlapping/garbled ("helicopter") audio during voicemail message playback on VoBiz calls
Constraint: This fix must be scoped strictly to the VoBiz voicemail-delivery path. Nothing else on the platform should be touched or altered — no changes to Twilio/Plivo AMD behavior, no changes to normal human-conversation call flow, no changes to dashboard/UI, no changes to other providers' streams or call handling. If a shared function/module needs modification, isolate the change so it only affects behavior when a VoBiz voicemail is being delivered, and verify no other call path's behavior changes as a result.
Investigate and fix, in this order:

Tear down the acoustic confirmation listener before playback. The moment "confirmed machine" fires, fully stop and close the VAD/speech-energy analysis loop from the confirmation phase before deliverVoicemail() starts speaking. Confirm via logs that no confirmation-phase events are still firing once playback begins.
Check for duplicate media streams on the same call leg. Verify only one WebSocket/media stream is open per CallUUID during voicemail delivery. If both the original answer-webhook path and the async machine_detection_url callback path can each open or write to a stream, ensure only one ever does — the second signal should only confirm/log, never open a second audio path.
Enforce single-resolution before any playback trigger, not after. In the AMD state machine, make sure the "already resolved, ignore late/duplicate signal" check happens strictly before any call to deliverVoicemail() — not concurrently with or after — so a late VoBiz callback can never trigger a second overlapping playback of the voicemail message.
Verify audio format consistency on the TTS send path. Confirm the voicemail message audio is encoded/sampled at the exact rate and codec VoBiz expects for that call leg (e.g. 8kHz μ-law). A mismatch here can independently cause chopped/distorted audio.
Check RTP/WS frame pacing on the voicemail playback path. Ensure audio frames for the voicemail message are sent at real-time pace, not faster/bursted, and not out of order.
